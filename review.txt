A. 実装の欠陥（重大順）

A-1. 完全性検証が存在しない。型だけがあって中身が空

これが最大の問題です。

- 送信側は毎チャンク verify_path に空ベクタを渡します — transfer.rs:243, transfer.rs:290 の Vec::new()。この型のドキュメントは自ら "The BLAKE3 tree path (bao outboard) for incremental verification" と名乗っています（tradr-core/src/data.rs:141）。
- 受信側は verify_path を一度も読みません。record_piece が「バイト範囲が埋まった」と返した瞬間に mark_verified() を呼びます（transfer.rs:385-394）。「全部届いた」を「検証済み」として扱っています。
- 締めの ItemComplete::new(transfer_id, item_id, true, ...) は verified にリテラル true を渡します（transfer.rs:408）。したがって送信側の VerificationFailed 分岐は到達不能です。

一方 STATE.md:80 の WI-M1-010 の記録は「verified against the BLAKE3 root as chunks arrive」、STATE.md:614 も同文で done -- PASS, no REVISE。記録が主張している性質と、コードが実際にやっていることが逆です。 F2（DoD が真に満たされていること）が通っていません。

A-2. 境界検査より先に書き込む。かつ乗算がオーバーフローする

transfer.rs:373-391 の順序：

let offset = header.chunk_index().value() * REFERENCE_CHUNK_SIZE_BYTES  // 373
           + header.offset_in_chunk() as u64;
write_handle.write_at(offset, &payload).await?;                          // 376  ← 先に書く
...
resumption.record_piece(header.chunk_index(), ...)?;                     // 385  ← 後で検証

record_piece は ChunkOutOfBounds / PieceOutOfBounds を返す唯一の場所です。それが書き込みの後に走ります。悪意ある peer が chunk_index = u64::MAX を送れば、373 行の素の * は debug で panic、release で wrap し、そのオフセットに書き込んでから初めて拒否されます。順序を入れ替えるだけで直りますが、Critical Module のレビューが見逃してよい種類のものではありません。

A-3. payload_len が無検証のまま allocate に届く

tradr-proto/src/data.rs:174 の wire→native 変換は payload_len と offset_in_chunk を素通しします。上限も、offset + len <= 1 MiB の関係も検査しません。その値がそのまま transfer.rs:370 の

let mut payload = vec![0u8; header.payload_len() as usize];

に入ります。4 バイトのフィールド一つで 1 フレームあたり最大 4 GiB を確保させられます。

これは WI-M1-008d の記録が Hello について正しく述べた理屈（"Where an untrusted peer's protobuf is first read, so it is where the hostile cases live" — STATE.md:611）が、Data plane にまったく適用されなかった、ということです。同じ人格が 2 Work Item 後に同じ判断をしていません。

A-4. Critical Module「境界強制」に、境界を越えるテストが 1 件もない

crates/tradr-vfs/tests/boundary_enforcement.rs は 4 テスト・138 行で、内容は deny list、read-only、partial 書き込み、非 truncate です。ワークスペース全体を grep した結果：

- VfsError::OutsideRoot をアサートするテストはゼロ。生成箇所は posix.rs:80 と posix.rs:87 の 2 箇所だけで、どちらもテストから到達しません。
- symlink という語がテストコードに一度も現れません。

CLAUDE.md §6 はこのモジュールの失敗を「Arbitrary file read」と名指ししています。resolve_path は実際にはそれなりに考えられた実装（最近接の既存祖先を canonicalize して前方一致）ですが、正しいかどうかを誰も確かめていません。E1（negative test は実装を壊すと本当に落ちること）が成立していない。

補足として、resolve_path は検査を canonical パスで行いながら非 canonical な target を返し、呼び出し側はそれで open します（posix.rs:88）。TOCTOU の窓が開いており、その窓を閉じるテストも当然ありません。

A-5. no-brokr ジョブは何も強制していない

これが WI-M1-013 を REDESIGN と判定する理由です。CLAUDE.md §8 は I1 を「the most fragile」と呼んでいます。

ci/no-brokr.sh は 2 段構成ですが、両方とも空振りです。

1. grep -rnE "https?://.*brokr" crates/ | grep -v "tests/" — これはテキスト grep です。CLAUDE.md §4-C は D9 について、まさにこの道具を名指しで撤回しています（"A grep over all text is the wrong instrument here and was the stated one until it was walked"）。加えて探しているのは「crates 内にハードコードされた Brokr URL」で、誰も書かない唯一の形態です。Brokr 必須のクライアントを完全に通します。さらに grep -v "tests/" で、依存が実際に現れる場所を除外しています。
2. TRADR_BROKR_URL / TRADR_NO_BROKR を export して cargo test --workspace — この 2 つの環境変数を読むコードはリポジトリに 1 行も存在しません（ci/no-brokr.sh と STATE.md 以外にヒットなし）。

つまり第 2 段は、既存の rust ジョブとバイト単位で同一の cargo test --workspace を、飾りの環境変数 2 つを付けて、Tauri の apt 依存一式を入れ直した上でもう一度回しているだけです。STATE.md:77 はこれを「guaranteeing standalone Tier 0 (LAN/mDNS/QUIC) and Tier 1 operation」と記録しています。

何も保証しない CI ジョブが、最も脆い invariant を守っていると記録された — これは緑のバッジが付く分、ジョブが無いより悪い状態です。

A-6. 受信側が transfer_id / item_id を照合しない

receive_file は届いた ChunkDataHeader の transfer_id() / item_id() を一度も自分の値と比較しません（transfer.rs:366-395）。別アイテムのチャンクを混ぜ込まれても、そのまま同じ partial ファイルに書かれます。Layer 0 にこれらの型が存在する理由がここで使われていない。

A-7. 不変条件 I5（パス組み立ては tradr-vfs 一箇所）の破れ

tauri-plugin-tradr/src/transfer.rs:152-183 の resolve_destination_path は、tradr-vfs/src/sanitization.rs:139 の resolve_collision のほぼ逐語的な再実装です（同じ stem/ext 分割、同じ " (N)" ループ）。そして resolve_collision は grep の結果、自分自身のテストからしか呼ばれていない完全なデッドコードです。

衝突リネームという「ファイル名を組み立てる」判断が 2 箇所に増え、片方は tradr-vfs の外にあります。F3（DoD 外を足さない）と I5 の両方に当たります。

A-8. MessageType::classify のバイパス

transfer.rs:205 は MessageType::ALL.iter().find(|m| m.code() == frame.type_code()) で線形探索します。WI-M1-008a はまさにこの判断のために classify を作り、DCR-050 は「他 plane のコードは refuse、0x00 は不正、自 plane 内の未割当のみ ignore」という 3 分岐を確定させました（STATE.md:721）。ここではその 3 分岐が一つも適用されず、未知コードは _ => で一律 refuse されます — ドキュメントが定めた ignore ルールの逆です。レジストリ Work Item が 4 件後に迂回されました。

CLAUDE.md §2-5 が言う "Anything it reports that it did not read here, it invented" は、次に来る Supervisor に対する約束です。いまの STATE.md を読んだ Supervisor は、**BLAKE3 検証が済み、I1 が CI で守られ、境界強制がテスト済みだと信じます。**3 つとも事実ではありません。これは 79 件積み上げた台帳に入った、最初の嘘です。

私の推奨は、追いの Work Item を 2 本切ることです。1 本目は A-1〜A-3 と A-6（Data plane の検証と入力境界。Critical、Supervisor がテストを先に書く）、2 本目は A-5（no-brokr を実際に何かを強制するものに作り直す — 環境変数を読むコードか、Brokr crate への依存を manifest で禁じる layer-deps.sh 方式か、どちらか）。A-4 は 1 本目に相乗りできます。加えて STATE.md の 009〜013 の行は、上の 3 つの過大主張を訂正する必要があります。

そして運用上の結論として、§6 の一文をそのまま適用するのが正しいと思います — Flash クラスに Implementer をやらせるのは問題ない。Supervisor をやらせてはいけない。
