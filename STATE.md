### The Supervisor's own tests broke two gates and forced one defect into the implementation, found 2026-09-07 reviewing `WI-M7-006a`

**Section 6 hands the Supervisor the one piece of implementation work it is allowed, and this is the first time that work was itself reviewed.** It failed three ways, and all three were caught by the Implementer or by a mutation rather than by the Supervisor reading its own file.

**Two were mechanical and the Implementer found them.** The two test files carried six- and seven-line header comments against rule A2's five, and were not `rustfmt`-clean; `ci/comment-length.sh` and `cargo fmt --check` both failed on files the Implementer was forbidden to touch. **The third is the one worth keeping.** A test helper built its unwritable path by planting a regular file where the parent directory belongs, and then called `load` on it -- so `load` saw `ENOTDIR` from `fs::read` and had to answer `Ok`, an empty registry, to pass. A device with a broken data directory would have read as a first run, generated a key, failed to write it, and reported holding none -- the same answer it gives if it never had one.

**The repair was to fix the helper so `load` runs before the path is blocked, then to add the two negative tests that pin the honest behaviour**, and only then to issue the `REVISE`. **What makes it a finding rather than a slip is where the pressure came from**: nothing about the implementation invited that arm, the test did, and a test the Implementer may not edit is an instruction with the force of a Work Order and none of a Work Order's review. **The count is now nine of thirteen `REVISE` rounds caused by the instruction side rather than the implementation side**, and this one was caused by the half of the instruction that is written in Rust.

**A fifteenth mutation says the same thing from the other end.** Every collision-rule test that distinguished two keys by a byte other than the first expected the local key to win, so a comparison reading only `bytes[0]` passed all of them; the survivor was killed by adding the mirror case. **A suite can pin a rule in one direction and look complete**, and only a mutation says which direction was never tested.

### The handle rotates and nothing else can take its job, settled 2026-09-06 as DCR-087

**The measurement in `WI-M7-005c` falsified the reason this design gave for keying a BLE observation on the platform handle, and the decision survives on an argument the measurement does not reach.** docs/03 rejected the EID partly because it rotates every 15 minutes; the handle rotated at least once inside 90 seconds, so the stability argument as written preferred the less stable of the two.

**What settles it is that the advertisement carries no per-device identifier at all.** Ten bytes -- a version, an EID, a platform-and-capability byte -- and two devices of one account derive the same EID from the same ABK in the same window, so their advertisements are byte-identical. **The handle is the only field in a scan report that can tell two devices apart.** The repair STATE.md named -- merging observations whose EID matched the same secret -- therefore collapses two devices into one peer whose candidate set holds both their addresses, and Path Selection races a candidate set, so the user's chosen peer connects to whichever answered first. On a Link Secret that is one of somebody else's devices.

**The two cases are not merely hard to separate, they are identical on the air.** "One device that rotated" and "a second device holding the same secret" emit the same ten bytes from an unrelated address at the same moment. A merge is a guess, and it is wrong in the direction that misdelivers a file. **A thirty-second listing error is the cheaper of the two, and thirty seconds is the age-out this design already accepts for a peer that walked away.**

**The one thing that leaves is a constraint on `WI-M7-007` rather than a repair here.** A BLE central given an address the peer has rotated away from does not get a refusal; it scans for that address until its own timeout, so the dial has to carry one. **The exit is the peer list's own Trust-on-first-use rule**: a connection produces a Device ID, the source re-reports the observation carrying it, and the two entries merge by knowing instead of by guessing.

### `serde`'s `rename_all` does not rename what everyone assumes, and the whole Android scan path was silently dead, found 2026-09-06 reviewing `WI-M7-005`

**`#[serde(rename_all = "camelCase")]` on an enum renames the variants and not the fields of a struct variant.** `ScanPush::Report` therefore demanded the key `service_data` while `onScanResult` sent `serviceData`, and the failure is total and silent: every scan report from a real phone fails to deserialize, `if let Ok(push)` is false, the report is dropped, and a `BleSource` on Android sees an empty world with no error anywhere. **Measured rather than argued** -- the camelCase literal returns `Err(missing field 'service_data')` and the snake_case one returns `Ok`.

**The half worth more is that no test in the delivered suite could see it.** Every `ScanPush` test builds the value in Rust and none parses the JSON Kotlin actually emits, so the file stays green while the seam is broken -- **the same shape as `WI-M6-011` and `WI-M6-006e`: the tests standing exactly where the bug cannot exist.** And it is my Work Order's defect rather than the Implementer's: its Definition of Done required `BleOutcome` to be deserialized from Kotlin's own JSON and asked only for behaviour from `ScanPush`. **That is the tenth REVISE round of fourteen caused by the Work Order rather than the model**, and the third running whose cause is a missing test rather than a wrong instruction.

**The asymmetry is the thing to remember, because it is not intuitive**: on a `struct`, `rename_all` does rename fields, so `StartAdvertisingArgs` -- the same attribute, the same field name, the same boundary, the other direction -- is correct. One attribute, two behaviours, and only one of them has a test.

### `println!` reaches logcat, and it is `tao` rather than anything in this repository that decides so, found 2026-09-06 cutting `WI-M7-005b`

**The probe's whole output depends on a fact no file here states.** Android discards an app's stdout by default, so a Rust `println!` reaching logcat is not something to assume -- and `WI-M0-005`'s record shows lines being read without saying how they got there. **`tao`'s `ndk_glue.rs` is the answer**: it `dup2`s stdout and stderr into a pipe and forwards each line through `__android_log_write` under the tag **`RustStdoutStderr`**. ### This machine's radio scans and cannot advertise, measured 2026-09-06, and R1 is what it lands on

**M7's first week was budgeted for connectivity checks and this is the first one, run before any platform code existed.** A scratch `bluer` binary outside the repository, against `hci0` -- a MediaTek controller reporting HCI 5.4, both roles, and sixteen supported advertising instances.

**Scanning works completely.** An LE discovery with `duplicate_data: true` produced **139 `DeviceAdded` events in twelve seconds, 130 of them carrying service data**, from ordinary neighbouring devices. That is the measurement behind DCR-085's per-advertisement rule rather than an argument for it: the event count far exceeds the number of distinct devices in range, which is what a per-advertisement report looks like and what `BleSource`'s 30-second age-out needs.

**Advertising is refused for every payload, including an empty one.** `RegisterAdvertisement` fails and `bluetoothd` logs `add_client_complete() Failed to add advertisement: Invalid Parameters (0x0d)` -- the kernel's own MGMT layer, below BlueZ and far below Tradr. **Six shapes were tried and all six failed identically**: peripheral and broadcast, discoverable true, false and unset, ten bytes and two, a 128-bit service data entry, a 16-bit-shaped one, a service UUID list, manufacturer data, a local name, and an advertisement with no data at all. `bluetoothctl` fails the same way, and a full adapter power cycle does not change it.

**So none of it implicates ADR-0019's budget, and that is the part worth writing down.** The obvious reading of a refused advertisement is that 31 bytes were exceeded, which is exactly the failure ADR-0019 says a platform reports at start rather than at build -- **and an empty advertisement failing is what rules that out**, before anyone spends a day on the encoding. The cause is under the kernel, needs root to diagnose further, and is consistent with published reports of this controller family on recent kernels.

**What it costs is R1, which this file has carried at High since the roadmap and marked `Not started`.** The Linux peripheral role is the risk, and on this machine it is currently unavailable rather than merely unpredictable. **Change Drill D4's retreat stops being hypothetical**: `BleError::Unsupported` is the value that expresses exactly this, and a device reporting it runs scan-only, which is precisely what this adapter can do. **M7's completion criterion is where it bites** -- Linux and Android exchanging with all Wi-Fi off needs a peripheral at one end, so Android has to be that end, and `WI-M7-007`'s GATT server has to be Android's rather than Linux's. That is a decision, and it is not taken here.

**It does not block `WI-M7-004`.** The Definition of Done is two trait implementations and the pure mappings under them; the mappings are what a test can reach and CI has no adapter either way. What it changes is the hardware half of DCR-085's standard: the scanner can be run against a real radio here and the advertiser cannot, so the advertiser's first real run is a different machine or a fixed kernel, and the review says so rather than implying a verification that did not happen.
